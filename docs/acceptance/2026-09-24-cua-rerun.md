## Product bugs and findings

**Bug A (new) — Medium. A screenshot of a shared tab that is not the active tab hangs until Chrome repaints it, and blocks later commands.**
- **Repro.**
  1. Share any tab.
  2. Activate a different tab in the same window, and leave the popup closed.
  3. Run `rt browser_take_screenshot '{}'`.
- **Observed.**
  - No result arrives; the CLI returns `timeout` "Timed out waiting for peer" after 120 s. This happened 3 times out of 3.
  - Commands sent after it, such as a snapshot, also wait.
  - The result is delivered as soon as something makes Chrome paint: activating the shared tab, or opening the extension popup. Opening the popup is not a visible change to the shared tab.
  - The delivered image does show the shared tab.
- **Not affected.**
  - A snapshot on its own from a background tab returns in about 1 s.
  - A screenshot of the shared tab while it is the active tab of a window hidden behind another window returns in 1.2 s.
- **Likely cause.** `Page.captureScreenshot` in `packages/extension/src/driver.ts` has no timeout. Chrome does not produce a frame for a hidden tab, so the command loop waits indefinitely.
- **Why it matters.**
  - The plan requires this screenshot to work while the human uses another tab.
  - An agent in this situation stalls for 2 minutes and then gets a misleading `timeout`.
  - A result that arrives late is applied to a command the CLI already gave up on.
- **Environment caveat.** This may be worse under Xvnc and Chrome for Testing than on a desktop Chrome. The previous run saw it once and it did not reproduce then (its Obs. C). It reproduced every time here.
- **Possible fixes.** Bound the capture with a timeout that returns a clear error, or skip or queue screenshots for hidden tabs.
