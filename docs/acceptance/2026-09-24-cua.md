## Product bugs and findings

**Bug 1 (#45) — Medium. An active share stopped by itself, with no recorded reason.**
- **What happened.** Profile A's first Act share, `c27dae85…`, stopped within about 15 s of the profile-B used-code check. Nobody stopped it: there was no human Stop, no agent `stop`, the TTL had 27 min left, and the tab was still open. The first agent command (`browser_snapshot`, seq 2) got `session_not_active` and no result was ever posted. The interaction summary shows "Verified stopped session history" with no reason for the stop.
- **Probable cause (hypothesis, not proven).** The default anonymous limit of 10 QPS per IP was exceeded; the server logged 429 `throttled` events that same minute (3 at 03:43). `peer.ts` retries a 429 only for replayable bodies, and only within the remaining deadline. Otherwise `RemoteTabError("rate_limited")` reaches the extension command loop (`session.ts`, the catch around the command loop), which sets "Connection ended. Start a new share to continue." and calls `stop()`.
- **Reproduction.** Did not reproduce in 2 retries. Minimal attempt: run the server with anonymous access at the default QPS; run the extension and the agent CLI from the same IP; poll `status`/`wait-ready` and send commands back to back.
- **Why it matters.**
  - Real single-machine setups (agent and Chrome on one host or NAT) share that bucket, and a transient 429 should not end a consented share.
  - The ledger and summary should record why a share stopped, so an unexplained stop can be diagnosed.

**Bug 2 (#46) — Low (spec vs. implementation).** A valid agent token on the browser-only `POST /v1/sessions/{id}/extend` gets **401** `unauthorized` ("token not valid for this session"). The plan expects 403. `authSession()` in `packages/server/src/app.ts` returns 401 for a valid token of the wrong role. The denial itself is correct and expiry was unchanged. Either return 403 for an authenticated but wrong role, or correct the plan.

**Bug 3 (#47) — Low (privacy, best effort).** On the privacy fixture, the snapshot text shows the password field's rendered bullets (`StaticText "••••••••••••••••"`, 16 bullets for a 16-character dummy). That discloses the password's length to the agent. The OTP and card nodes are `[redacted]`, and no value leaked. Repro: Full share, then `/privacy`, type a password of length N, then `browser_snapshot`; the text contains N bullets.

**Bug 4 (#48) — Low (UX).**
- The popup's notice line keeps stale text:
  - "Tool is not allowed in the shared mode" stays while sharing continues;
  - "Paused by you at 03:51:58 UTC" still shows after Resume;
  - after that share was stopped, the next share's consent form still showed it.
- Pluralization: "Ends in 1 minutes", "1 entries".
- The toolbar tooltip "Remote Tab" can cover the popup's **Stop** button while the pointer hovers the action icon.

**Obs. A — debugging infobar absent.** No Chrome "debugging this browser" bar appeared at any point, although `chrome.debugger.attach` succeeded and CDP control worked. This may be a Chrome for Testing 154 or `--load-extension` behaviour rather than a product defect. It blocks the plan's bar-visibility and dismissal checks, and would need checking on branded Chrome with a real human.

**Obs. B — issue #28 not reproduced.** The agent's own `browser_click` and `browser_drag` did **not** trigger "Paused: you took over" in this X11 setup.

**Obs. C — one slow screenshot.** The first agent screenshot of the background shared tab took more than 20 s: the CLI call was cut off by the 28 s sandbox shell cap, and the result arrived later. The same call then took about 2 s. It did not reproduce; the likely cause is a background-tab capture being throttled.
